# Wire Protocol

The `server` binary exposes a raw binary HTTP API — no JSON anywhere on the
hot path. This is the single source of truth for the wire format; it is
generated by reading `src/api.rs`, `src/board.rs`, `src/game.rs` and
`src/moves.rs` directly, not copied from an external spec. (The route table
and every handler live in `src/api.rs`; `src/server.rs` is only the `main`
that binds a listener to `api::router`.)

Successful responses use `Content-Type: application/octet-stream`. Error
responses are `text/plain; charset=utf-8` and carry a short, caller-facing
explanation of what was wrong with the request — never internal state.

`tests/protocol_conformance.rs` asserts every byte offset and bit position on
this page against hardcoded expectations. Change the format and that suite
fails; change this page without changing the format and nothing does, so keep
them in step by hand.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `PORT` | `3000` | listen port |
| `KERES_API_TOKEN` | unset | when set, every route except `/health` requires `Authorization: Bearer <token>`; a mismatch is `401` with `WWW-Authenticate: Bearer` |
| `KERES_CORS_ALLOWED_ORIGINS` | `*` | comma-separated allow-list; the default permits any origin |
| `KERES_MAX_HISTORY_MOVES` | `4096` | cap on a replayed move history |
| `KERES_MAX_CONCURRENT_SEARCHES` | `2` | engine searches allowed to run at once |
| `KERES_SEARCH_TIMEOUT_SECS` | `60` | wall-clock budget for one search |

**The defaults are wide open**: no authentication, any origin. The engine is
expected to sit behind a trusted caller (e.g. keres-platform), not to be
exposed directly to end users — see `SECURITY.md`. Setting a token while
leaving CORS at `*` logs a warning at startup.

## Board dimensions

- `BOARD_DIMENSION = 9` (9×9 board)
- `BOARD_SIZE = 81` (`BOARD_DIMENSION²`)
- A `Position` is `y * 9 + x`, encoded as a single `u8` in `0..=80`.

## Piece encoding — 1 byte per square

```
bit:    7  6  5  4  3  2  1  0
        0  C  U  U  U  L  L  L
```

- `0` = empty square.
- `C` (bit 6): `1` = White, `0` = Black.
- King: special-cased as `C 111 000` (bottom=King, no top — the king can
  never be stacked).
- Otherwise: `LLL` = bottom piece type (3-bit `PieceType` discriminant),
  `UUU` = top piece type of the stack, or `000` if unstacked (a single
  piece is never confused with an "unstacked King" because King always
  uses its dedicated `111 000` pattern).

`PieceType` discriminants (`src/board.rs`): `Soldier=1, Bishop=2, Rook=3,
Paladin=4, Guard=5, Knight=6, Ballista=7` (`King` has no ordinary
discriminant — it only ever appears via the special byte above).

## Game (board + turn state) — 83 bytes

`Game::to_binary()` / `Game::from_binary()`:

| Bytes | Content                                                                                |
|-------|------------------------------------------------------------------------------------------|
| 0–80  | 81 board squares, one byte each (see piece encoding above)                               |
| 81    | Flags byte: `0x80` white-to-move, `0x40` game-over, `0x20` white-wins, `0x10` draw       |
| 82    | `moves_without_capture` counter (`u8`); the game is a draw at `>= 40`                     |

This is the `BOARD_SIZE + 2` = 83-byte format sent/received by `/new`,
`/moves`, `/play`, `/replay-moves`, `/engine-move-board`.

Decoding is strict in both directions of the format's slack: a square byte
with bit 7 set, or with `LLL == 000` outside the king's dedicated `C 111 000`
payload, is rejected, as is a board carrying more than one king of a colour.
A payload that is not exactly 83 bytes is rejected on length alone.

## Move — 2 bytes (`u16`, little-endian)

Two different bit layouts share the same 16-bit slot depending on direction:

**Server → client** (`/moves` response — a `PotentialMove`, `moves.rs`):

```
bit 15: force_unstack   bit 14: unstackable   bits 7-13: to (7 bits)   bits 0-6: from (7 bits)
```

- `unstackable`: this move can legally be played either stacked or
  unstacked — the client must offer the choice (the platform's UX shows a
  confirmation dialog, defaulting to "full stack").
- `force_unstack`: the destination forces the top piece to separate;
  only the unstacked variant is legal.

**Client → server** (`/play`, `/engine-move-*` request/response — a `Move`,
`moves.rs`):

```
bit 14: unstack   bits 7-13: to (7 bits)   bits 0-6: from (7 bits)
```

To play a move: take a `PotentialMove` from `/moves`, decide `unstack`
(`true` only if `unstackable` or `force_unstack` was set), then re-encode as
a plain `Move` with bit 14 = that boolean (bit 15 unused/zero) before
sending it to `/play`.

`force_unstack` set without `unstackable` is not a representable
`PotentialMove` — the generator never produces it and the decoder rejects it.
Bit 15 must be zero in a `Move`: a `PotentialMove` sent where a `Move` is
expected is rejected rather than silently truncated.

## Endpoints

| Method | Path                 | Request body                                          | Response body                                   | Max body |
|--------|----------------------|--------------------------------------------------------|--------------------------------------------------|----------|
| GET    | `/health`            | —                                                        | `ok\n` (`text/plain`) — liveness probe, never behind auth | — |
| GET    | `/new`               | —                                                        | 83 bytes: a fresh `Game`                          | — |
| POST   | `/moves`             | 83 bytes: `Game`                                         | `N × 2` bytes: legal `PotentialMove`s (LE `u16`s) | 83 B |
| POST   | `/play`              | 85 bytes: 83-byte `Game` + 2-byte `Move`                 | 83 bytes: the resulting `Game`                    | 85 B |
| POST   | `/replay-moves`      | `N × 2` bytes: `Move` list from the initial position     | 83 bytes: the resulting `Game`                    | (cap+1)×2 B |
| POST   | `/engine-move-board` | 83 bytes: `Game`                                          | 2 bytes: the engine's chosen `Move`                | 83 B |
| POST   | `/engine-move-game`  | `N × 2` bytes: full `Move` history from the initial position | 2 bytes: the engine's chosen `Move`           | (cap+1)×2 B |
| POST   | `/engine-move-game/:level` | `N × 2` bytes: full `Move` history from the initial position | 2 bytes: the engine's chosen `Move`     | (cap+1)×2 B |

`cap` is `KERES_MAX_HISTORY_MOVES` (default 4096). A history one move over the
cap gets a `400` naming the cap; a body larger than the per-route limit is
refused by the transport layer with `413` before any handler runs.

`/engine-move-game` replays the given move list from a fresh `Game`,
reconstructing the position-hash history so the search's loop/repetition
detection sees the same game the caller has been playing (`/engine-move-board`
has no history, so it cannot detect repetition draws). Both run
`root_search` at `MAX_DEPTH` (`src/engine/constants.rs`) and respond
`409` if no legal move exists (i.e. the game is already over).

`/engine-move-game/:level` is identical to `/engine-move-game` except the
integer path segment picks an engine strength level (`SearchConfig::for_level`,
`src/engine/types.rs`) instead of always searching at full power — the same
1 (weakest) .. 10 (full strength) scale as the native GUI's difficulty
slider, spanning search depth, quiescence/killer-move heuristics, a chance
of playing a shallower search's move, and noise among near-equal moves.
Level 10 is identical to the unleveled endpoint. `:level` outside `1..=10` gets `400`
(unlike the GUI slider, the API doesn't silently clamp an out-of-range
value). There is no leveled variant of `/engine-move-board` — it has no
game history, so it's only used to estimate a position, not to play a move
on a difficulty-limited opponent's behalf.

## Status codes

| Status | When |
|--------|------|
| `200` | success |
| `400` | wrong body length, undecodable board/game/move, a history that is not a whole number of moves or is over the cap, `:level` outside `1..=10` |
| `401` | `KERES_API_TOKEN` is set and the `Authorization: Bearer` header is missing or wrong |
| `404` / `405` | unknown path / wrong method |
| `409` | the request was well-formed but the position refuses it: an illegal move, a game that is already over, no legal move to search |
| `413` | body over the route's limit (see the table above) |
| `500` | a panic caught by the outermost layer — a bug; please report it (`SECURITY.md`) |
| `503` | the engine is saturated (no search slot within the queue timeout) or the search exceeded `KERES_SEARCH_TIMEOUT_SECS` |

A malformed payload is never a `500`. Every decoder on this path is fallible,
and `tests/api_robustness.rs` fuzzes each route asserting exactly that.

## AI search

See `src/engine/search/` — Negamax with alpha-beta pruning
(`alpha_beta.rs`, `negamax.rs`), quiescence search past the horizon
(`quiescence.rs`), a transposition table (`tt.rs`), killer-move ordering
(`killer.rs`), and repetition/loop detection fed by the caller-supplied game
history (`loop_detection.rs`). Search is parallelized with
[Rayon](https://github.com/rayon-rs/rayon). `root_search` (`search/mod.rs`)
is the entry point used by both engine-move endpoints and by the `keres`
CLI's `engine-move`/`debug-tree` subcommands.
